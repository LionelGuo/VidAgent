# vLLM-Omni 原生视频输入接口工程接入参考文档

**适用模型**：`Qwen3-Omni-30B-A3B-Thinking` (及其他支持视频输入的 Qwen-Omni 变体)
**适用框架**：`vLLM-Omni`
**文档版本**：v1.0

## 1. 概述
在 vLLM-Omni 框架下，视觉与文本处理采用多阶段解耦编排，开发者**无需手动对视频进行切帧、特征提取等预处理**，可直接将视频介质输入给框架。目前系统提供两种维度的视频接入方案：
1. **REST API (`/v1/chat/completions`)**：适用于离线长短视频分析、单次问答（VQA）、文件级视频理解。
2. **WebSocket Stream API (`/v1/video/chat/stream`)**：适用于实时摄像头推流、低延迟交互、边看边问、长视频动态上下文缓存。

## 2. 服务端启动配置规范
为了使框架原生支持本地视频的高效加载（避免 Base64 编码带来的极大 CPU 与网络开销），启动服务端时**必须显式挂载本地媒体路径并开启 omni 模式**。

**推荐启动命令（生产环境）：**
```bash
vllm serve Qwen/Qwen3-Omni-30B-A3B-Thinking \
  --omni \
  --trust-remote-code \
  --port 8000 \
  --allowed-local-media-path /data/media_storage \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.9
```
*   **`--omni`**：开启 Omni 多模态处理流水线。
*   **`--allowed-local-media-path`**：【关键参数】允许 vLLM 读取的本地绝对路径。出于安全规范，**禁止在生产环境配置为 `/`**，应配置为应用服务器专用的存储挂载目录（如 `/data/media_storage`）。
*   **`--max-model-len`**：视频 Token 占用极高，建议设置为模型支持的较大值（如 32K 或 64K）。

## 3. 接口模式一：REST API (标准离线请求)

### 3.1 适用场景
上传已有视频文件进行内容总结、动作识别、细节查找等非实时交互场景。兼容标准 OpenAI 多模态协议。

### 3.2 媒体 URL 支持格式
在 `video_url.url` 字段中，支持以下三种协议：
1. **本地文件（推荐性能最佳）**：`file:///data/media_storage/sample.mp4`
2. **网络链接**：`http://或https://.../video.mp4` (需保证部署 vLLM 的服务器能访问该外网链接)
3. **Base64**：`data:video/mp4;base64,xxxx...` (仅限小视频，大视频易导致 OOM 或请求超时)

### 3.3 Python SDK 调用示例
```python
import os
from openai import OpenAI

# 初始化客户端，指向 vLLM-Omni 服务端地址
client = OpenAI(
    api_key="EMPTY", # vLLM 默认不需要鉴权，或配置为实际的 API-KEY
    base_url="http://localhost:8000/v1",
)

def analyze_video(video_path: str, prompt: str) -> str:
    """
    通过 REST API 请求视频分析
    """
    # 构造 file 协议前缀
    local_file_uri = f"file://{os.path.abspath(video_path)}"
    
    try:
        response = client.chat.completions.create(
            model="Qwen/Qwen3-Omni-30B-A3B-Thinking",
            messages=[
                {
                    "role": "user",
                    "content": [
                        {
                            "type": "video_url",
                            "video_url": {
                                "url": local_file_uri
                            }
                        },
                        {
                            "type": "text",
                            "text": prompt
                        }
                    ],
                }
            ],
            # 对于长视频解析，建议设置较高的超时时间
            timeout=120.0, 
            stream=False # 根据业务需求决定是否流式输出文本
        )
        return response.choices[0].message.content
    except Exception as e:
        return f"请求失败: {str(e)}"

# 执行测试
result = analyze_video("/data/media_storage/test_video.mp4", "详细描述视频中发生的核心事件，并给出你的推理过程。")
print(result)
```

## 4. 接口模式二：WebSocket 实时流式 API

### 4.1 适用场景
直播流监控、摄像头实时问答。此模式下，视频不是一个完整文件，而是由客户端不断拆帧（Frames）发送给服务端。服务端实时将视觉特征写入 KV Cache，实现极低的“首字延迟”（TTFT）。

**Endpoint**: `ws://<HOST>:<PORT>/v1/video/chat/stream`

### 4.2 交互协议 (Protocol Flow)
WebSocket 连接建立后，通信基于 JSON 格式的消息：

1.  **Client -> Server: `session.config`**
    初始化会话，告知服务端输入输出的预期模态（对 Thinking 模型而言，输出仅为文本）。
2.  **Client -> Server: `video.frame` (持续发送)**
    客户端根据自己的采样率（如 1 FPS），将视频当前帧压缩为 JPEG/PNG 的 Base64 发送。
3.  **Client -> Server: `video.query` (事件触发)**
    用户发起提问时发送。
4.  **Server -> Client: `response.text.delta` (服务端响应)**
    服务端流式返回推理的文本内容。

### 4.3 WebSocket 工程伪代码参考
```python
import asyncio
import websockets
import json
import base64
import cv2

async def real_time_video_chat(ws_url, video_source):
    async with websockets.connect(ws_url) as ws:
        # 1. 发送会话配置
        await ws.send(json.dumps({
            "type": "session.config",
            "modalities": ["text"],
            "model": "Qwen/Qwen3-Omni-30B-A3B-Thinking"
        }))
        
        # 2. 启动异步任务接收服务端结果
        async def receive_responses():
            async for message in ws:
                data = json.loads(message)
                if data["type"] == "response.text.delta":
                    print(data["text"], end="", flush=True)
                elif data["type"] == "response.done":
                    print("\n[回答完毕]")
        
        recv_task = asyncio.create_task(receive_responses())

        # 3. 模拟视频帧抽取与推送
        cap = cv2.VideoCapture(video_source)
        frame_count = 0
        while cap.isOpened():
            ret, frame = cap.read()
            if not ret:
                break
                
            # 每隔N帧抽取一次发送 (建议控制在 1 FPS 左右防止过多Token积压)
            if frame_count % 30 == 0:
                # 编码为 JPEG Base64
                _, buffer = cv2.imencode('.jpg', frame, [cv2.IMWRITE_JPEG_QUALITY, 80])
                frame_b64 = base64.b64encode(buffer).decode('utf-8')
                
                await ws.send(json.dumps({
                    "type": "video.frame",
                    "frame": f"data:image/jpeg;base64,{frame_b64}"
                }))
                
                # 演示：在特定的时间点（例如第90帧）提出问题
                if frame_count == 90:
                    print("\n[Client] 正在发起提问...")
                    await ws.send(json.dumps({
                        "type": "video.query",
                        "text": "基于刚刚出现的画面，详细分析图中的人物在做什么？"
                    }))
                    
            frame_count += 1
            await asyncio.sleep(0.03) # 模拟真实视频流的时间流逝

        cap.release()
        await recv_task

# 执行示例
# asyncio.run(real_time_video_chat("ws://localhost:8000/v1/video/chat/stream", "/data/media_storage/camera_stream.mp4"))
```

## 5. 针对 `Qwen3-Omni-30B-A3B-Thinking` 模型的特殊说明与优化建议

1. **纯文本推理特性 (Pure Thinker)**
   `Qwen3-Omni-30B-A3B-Thinking` 是专门针对长思维链（Chain-of-Thought）优化的版本。它**不具备**语音生成（TTS）的 Talker 能力。
   * **工程指导**：在业务逻辑处理时，无需监听和处理音频流的返回（`response.audio.delta`），仅需专注消费和渲染 `response.text.delta` 即可。

2. **KV Cache 与显存管理**
   视频作为一种富媒体，在转变为视觉 Token 后，会极大消耗系统的 KV Cache 显存。
   * **工程指导**：如果在生产环境遇到 OOM 或请求大面积 Pending，应当：
     - 减小 `max_model_len`（如果业务对极长视频没有绝对依赖）。
     - 增加服务器数量做横向扩展。
     - 如果通过 REST API 请求，尽量降低上传视频的时长和分辨率；如果是 WebSocket 推流，请合理控制帧率（如建议降至 1fps 或 0.5fps）。

3. **HTTP 超时配置 (Timeout Control)**
   使用 REST API 加载大型视频时，vLLM 底层的 Vision Encoder 处理耗时较长（特别是高分辨率长视频的前置编码阶段）。
   * **工程指导**：API Gateway（如 Nginx/Kong）及业务后端的超时时间（Timeout）必须相应拉长，建议设置为 60-120 秒，避免因反向代理超时导致连接被强制切断。
