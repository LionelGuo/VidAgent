> 更新：2026-08-14（C7 删除旧栈后重写——llama_proxy/Gradio 已删除，SSE Relay 内置于 FastAPI 后端）

## 架构总览

```
┌─────────────── AutoDL 服务器 (RTX 3090 48GB) ───────────────┐
│                                                              │
│  vLLM-Omni :6006                                              │
│  └─ Agent 主模型（文本 + tool calling）+ 多模态总结            │
│                                                              │
└──────────────────────┬───────────────────────────────────────┘
                       │ AutoDL 自定义服务 :6006 → :8443
                       │
┌─────────── 本机 / 部署服务器 ────────────────────────────────┐
│                                                              │
│  FastAPI 后端 :8000（SSE Relay 内置）                          │
│  ├─ /v1/chat/completions —— relay 分流（xml / transparent）   │
│  └─ /api/tools/* —— 检索 / 下载 / 总结 REST + SSE 进度         │
│                                                              │
│  Next.js 前端 :3000                                           │
│  ├─ Agent 对话 → 后端 relay → vLLM :8443                      │
│  └─ 总结 → 后端 /api/tools/summarize → vLLM :8443             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

> 旧版（llama_proxy :8081 + Gradio UI）已随 C7 删除：proxy 的 XML→tool_calls 转换逻辑内置于 `server/sse_relay.py`，由 FastAPI 承担；UI 由 Next.js 前端承担。

## 一、服务器端

### 1.1 SSH 登录

```bash
ssh -p <端口> root@connect.westd.seetacloud.com
```

AutoDL 实例需以**有卡模式**开机。

### 1.2 模型文件

模型路径：`/root/autodl-tmp/Qwen3-Omni-30B-AWQ`

| 文件 | 说明 |
|------|------|
| `config.json` | 模型架构：`qwen3_omni_moe`，量化：`compressed-tensors` INT4 |
| `*.safetensors` | 权重文件（~27.5 GB，6 个分片） |
| `preprocessor_config.json` | 音频/图像输入上限（已修改为支持 1h 音频） |
| `tokenizer.json` | Tokenizer |

### 1.3 启动 vLLM-Omni

vLLM 以 **bare mode** 运行（不传 `--enable-auto-tool-choice` / `--tool-call-parser`），让 Qwen3-Omni 自由输出文本（含 `<tool_call>` XML），工具调用的解析和转换由后端 SSE Relay 完成。

```bash
export VLLM_MAX_AUDIO_DECODE_DURATION_S=3600

nohup /root/miniconda3/bin/vllm-omni serve \
  /root/autodl-tmp/Qwen3-Omni-30B-AWQ \
  --port 6006 \
  --gpu-memory-utilization 0.85 \
  --max-num-batched-tokens 16384 \
  --max-num-seqs 8 \
  --enable-prefix-caching \
  > /root/autodl-tmp/server.log 2>&1 &
```

Thinking版本
```bash
/root/miniconda3/bin/vllm-omni serve   /root/autodl-tmp/Qwen3-Omni-Thinking-AWQ-4bit   --port 6006   --gpu-memory-utilization 0.85   --max-num-batched-tokens 49152   --max-num-seqs 2   --enable-prefix-caching   --allowed-local-media-path /root/autodl-tmp   --limit-mm-per-prompt '{"video": {"count": 1, "num_frames": 10}}'
```
也可直接使用仓库脚本：

```bash
bash /root/autodl-tmp/VidAgent/scripts/start_vllm_bare.sh
```

#### 参数说明

| 参数 | 值 | 说明 |
|------|-----|------|
| `VLLM_MAX_AUDIO_DECODE_DURATION_S` | `3600` | 环境变量，允许最长 60 分钟音频输入（默认仅 600s） |
| `--port` | `6006` | 服务监听端口 |
| `--gpu-memory-utilization` | `0.85` | GPU 显存使用比例（48GB × 0.85 ≈ 41GB 给 KV cache） |
| `--max-num-batched-tokens` | `16384` | 单次 batch 最大 token 数，提升 decode 阶段吞吐 |
| `--max-num-seqs` | `8` | 最大并发序列数 |
| `--enable-prefix-caching` | — | 复用相同前缀的 KV cache（Agent 长 system prompt 跨轮次受益） |

#### 启动耗时

约 5-7 分钟（208s 加载权重 + 112s 编译/CUDA graph 预热）。

#### 检查就绪

```bash
curl -s http://localhost:6006/health
# 返回空响应 + HTTP 200 = 就绪
```

### 1.4 已修改的配置

**`preprocessor_config.json`**：`n_samples` 从 4,800,000（300s）增至 57,600,000（3600s），支持 1 小时音频。

```bash
# 查看
cat /root/autodl-tmp/Qwen3-Omni-30B-AWQ/preprocessor_config.json | python3 -c \
  "import sys,json; c=json.load(sys.stdin); print(f'n_samples={c[\"n_samples\"]} ({c[\"n_samples\"]/16000}s)')"
```

### 1.5 AutoDL 自定义服务

在 AutoDL 控制台 → 实例 → 自定义服务，添加：

| 字段 | 值 |
|------|-----|
| 服务端口 | `6006` |
| 外部端口 | `8443` |

获取公网 URL 形如 `https://u<userid>-<instance>.westd.seetacloud.com:8443`。

## 二、本机端（FastAPI 后端 + Next.js 前端）

### 2.1 `.env` 配置

```bash
# provider 预设：vllm（自托管）—— bare mode 下 relay 走 xml 协议转换
LLM_PROVIDER=vllm

# Agent 端点（通过后端 relay，xml 模式）
OPENAI_BASE_URL=https://u<userid>-<instance>.westd.seetacloud.com:8443/v1
OPENAI_API_KEY=not-needed
LLM_MODEL=/root/autodl-tmp/Qwen3-Omni-30B-AWQ

# 多模态端点（留空则复用上面的 base_url + model）
# MULTIMODAL_BASE_URL=
# MULTIMODAL_MODEL=
```

#### 关键分离

| 功能 | 端点 | 原因 |
|------|------|------|
| **Agent 文本 + tool calling** | 后端 `/v1/chat/completions` → vLLM | relay 按 provider 预设分流（vllm=xml 协议转换 / siliconflow·generic=原生透传） |
| **多模态总结** | 后端 `/api/tools/summarize` → vLLM | 不需要 tool calling，流式透传即可 |

### 2.2 启动后端

```bash
cd /home/lionel/Code/VidAgent
uv run uvicorn server.main:app --host 0.0.0.0 --port 8000
```

### 2.3 启动前端

```bash
cd /home/lionel/Code/VidAgent/frontend
npm install
npm run dev        # http://127.0.0.1:3000
```

### 2.4 进程管理说明

后端 + 前端为两个独立进程，无内置编排：

- **后端**：`uv run uvicorn` 是包装进程，直接 kill 它 uvicorn 子进程会变孤儿继续占用 8000 端口——必须按监听 PID 操作：`ss -tlnp | grep :8000` 拿到 PID 再 kill。
- **前端**：`npm run dev` 为 next dev（生产用 `npm run build && npm start`）。
- 生产部署推荐 Docker 镜像（README「部署」节），入口 `docker/entrypoint.sh` 同时管理两个进程。

## 三、模型性能特征

### 3.1 实测速度

| 场景 | tok/s | 说明 |
|------|-------|------|
| 终端直接流式 | **~300** | `scripts/bench_stream.py` 直接连 vLLM |
| 通过后端 relay | **~300** | 无损耗（纯文本透传模式） |
| UI 端感知 | **~300** | SSE 逐 token 渲染，与模型速度一致 |

### 3.2 GPU 利用率说明

Qwen3-Omni-30B-A3B 是 MoE 模型（30B 总参数，每 token 仅激活 3B）。单请求时 GPU SM 利用率约 15-30%，这是**架构固有的正常表现**，瓶颈在显存带宽（3090 ~936 GB/s），不在计算单元。多请求并发时利用率会提升。

### 3.3 输入上限

| 模态 | 上限 | 说明 |
|------|------|------|
| 音频 | **3600s (1h)** | 已修改 preprocessor 的 `n_samples` |
| 图像 | 12.8MP/帧 | `max_pixels: 12845056` |
| 视频帧 | 768 帧 | `max_frames: 768` |
| Token 预算 | 65,536 | 所有模态共享 |
| 音频 token 消耗 | ~13 tok/s | 1h 音频 ≈ 46,800 tokens |

## 四、故障排查

### 后端返回 `Stream options can only be defined when stream=True`

relay 未正确删除 `stream_options`。检查后端日志（`server/sse_relay.py` 负责转发前清理）。

### UI 只输出 "思考中" 后停止

1. 确认 vLLM 服务器就绪：`curl https://<url>:8443/health`（空响应 + HTTP 200）
2. 确认后端可达：`curl http://127.0.0.1:8000/health`
3. 确认 `LLM_PROVIDER` 与实际端点匹配（vllm=xml relay；siliconflow/generic=transparent relay，用错协议流会异常）

### 工具调用不执行（输出 `<tool_call>` XML 文本）

1. 确认 `LLM_PROVIDER=vllm`（xml 模式才做 `<tool_call>` 解析转换）
2. 检查后端日志：`tail -f /tmp/vidagent-server.log`（或部署环境的后端日志）

### 抖音/小红书/快手检索无结果（CDP 连接问题）

1. 确认 Windows Chrome 以调试端口运行：`--remote-debugging-port=9222` 命令行启动，
   或 chrome://inspect 勾选开启；且平台已登录
   （快手未登录时 profile 接口返回 `result=109`，检索空结果）
2. **Chrome 146+ 调试模式不提供 `/json/*` HTTP 端点**：`curl http://127.0.0.1:9222/json/version`
   返回 404 属正常（调试走 WS `/devtools/browser`，与 `/json/*` 无关）。
   判断标准：Windows 上 `netstat -ano | findstr :9222` 显示 `chrome.exe` 在 LISTENING
   即正常；完全无监听（WSL 下 404 由 localhost 转发 relay 兜底响应）才是未开启
3. 每次后端重启后首次 CDP 连接，Chrome 会弹调试确认框，需 15 秒内点「接受」，
   超时未接受则连接失败，需再次重启后端

### GPU 显存不足

当前配置 `--gpu-memory-utilization 0.85`，已占 48GB × 0.85 ≈ 41GB。如需调整：

```bash
# 降低 KV cache 配额（会减小 max_model_len）
--gpu-memory-utilization 0.75

# 或限制最大并发
--max-num-seqs 4
```
